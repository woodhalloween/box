## 序論：高品質な動作解析システムを支えるテストスイートの全貌

ここに示された6つのテストファイルは、MediaPipeを用いたリアルタイム姿勢推定を基盤とする、高度な動作解析アプリケーションの品質保証を担うテストスイートの一部です。このシステムの目的は、カメラ映像から人間の骨格情報を抽出し、各関節の角度や体の傾き、さらには「首を振る」「長時間同じ姿勢でいる」といった複雑な動作パターンまでをリアルタイムで分析・評価することにあります。

このようなシステムにおいて、テストは極めて重要な役割を果たします。なぜなら、解析結果の僅かな誤差が、ユーザーへのフィードバック（例えば、リハビリテーション支援やトレーニングフォームの矯正、あるいは作業中の危険姿勢の警告など）の品質を大きく左右するからです。テストの目的は多岐にわたります。

1.  **正確性の保証**: 各計算ロジック（角度計算、状態判定など）が、与えられた入力に対して数学的・論理的に正しい出力を返すことを保証します。
2.  **堅牢性の確保**: 予期せぬ入力（ランドマークが検出できない、値が異常など）に対しても、システムがクラッシュすることなく、適切に処理を継続または終了できることを確認します。
3.  **依存性の分離**: MediaPipeやOpenCV、Pillowといった外部ライブラリに依存する部分を「モッキング」という技術で仮想的なオブジェクトに置き換えることで、これらのライブラリの仕様変更や不具合から隔離された、純粋な自作ロジックのみのテスト（単体テスト）を可能にします。これにより、テストの実行速度が向上し、問題の切り分けが容易になります。
4.  **保守性の向上**: テストコードは「動く仕様書」としての役割も果たします。各機能がどのような入出力を期待されているのかがテストケースとして明文化されているため、将来の機能追加やリファクタリングの際に、既存の機能を破壊していないか（デグレードしていないか）を即座に確認できます。

本解説では、`pytest`という高機能なテストフレームワークと、`unittest.mock`や`pytest-mock`といった強力なモッキングライブラリを駆使して構築されたこれらのテストファイル群を、一つずつ丁寧に解き明かしていきます。それぞれのテストが、アプリケーションのどの部分の信頼性を、どのようにして担保しているのかを、コードの細部に至るまで詳細に見ていきましょう。

## 第1章: `test_pose_estimator.py` - 姿勢推定の心臓部とのインターフェースをテストする

このテストファイルは、`src/pose_estimator.py`に定義されている`PoseEstimator`クラスを対象としています。`PoseEstimator`クラスは、GoogleのMediaPipeライブラリが提供する強力な姿勢推定機能（`mediapipe.solutions.pose.Pose`）をラップし、アプリケーション内でより扱いやすい形にカプセル化する役割を担っています。このクラスの責務は、画像を入力として受け取り、MediaPipeのエンジンを介して33個の身体ランドマークの座標（x, y, z, visibility）を抽出し、それをNumpy配列という標準的な形式で後続の解析モジュールに渡すことです。

このテストの核心は、**MediaPipeという外部の巨大な依存関係を完全に切り離し、`PoseEstimator`クラス自体のロジック、すなわち「MediaPipeを正しく呼び出し、その結果を正しく整形しているか」だけを検証する**点にあります。これを実現するために、`unittest.mock`の`patch`機能が全面的に活用されています。

### 1.1. テストの共通基盤: `mock_mediapipe_pose`フィクスチャ

```python
@pytest.fixture
def mock_mediapipe_pose():
    """mediapipe.python.solutions.pose.Poseをモック化するフィクスチャ"""
    with patch("mediapipe.solutions.pose.Pose") as mock_pose_class:
        mock_pose_instance = MagicMock()
        mock_pose_class.return_value = mock_pose_instance
        yield mock_pose_instance
```

このコードは`pytest`の**フィクスチャ**と呼ばれる機能で、テストケース間で共通して利用するセットアップ処理を共通化するためのものです。この`mock_mediapipe_pose`フィクスチャは、このテストファイルにおける最重要の役割を果たします。

-   **`@pytest.fixture`**: このデコレータにより、`mock_mediapipe_pose`という名前の関数がフィクスチャとして登録されます。各テスト関数がこの名前を引数として受け取ると、pytestはテスト実行前にこの関数を呼び出し、その返り値（`yield`される値）をテスト関数に渡します。
-   **`with patch("mediapipe.solutions.pose.Pose") as mock_pose_class:`**: `unittest.mock.patch`のコンテキストマネージャです。`"mediapipe.solutions.pose.Pose"`という文字列で指定されたオブジェクト（この場合は`Pose`クラス）を、`with`ブロックの期間中だけ`MagicMock`オブジェクトである`mock_pose_class`に置き換えます。これにより、テストコード内で`mediapipe.solutions.pose.Pose(...)`というコードが実行されても、実際のMediaPipeのクラスが呼ばれることはなく、代わりにこのモックオブジェクトが使用されます。
-   **`mock_pose_instance = MagicMock()`**: `Pose`クラスの*インスタンス*を模倣するための、もう一つの`MagicMock`オブジェクトを作成します。
-   **`mock_pose_class.return_value = mock_pose_instance`**: ここが重要なポイントです。`mock_pose_class`は`Pose`*クラス*のモックです。クラスが呼び出される（インスタンス化される）際の振る舞いは、`return_value`属性で制御します。この行は、「`mock_pose_class()`が呼び出されたら（つまり`Pose()`が実行されたら）、`mock_pose_instance`を返しなさい」という指示です。これにより、`PoseEstimator`の`__init__`内で`self.pose = mp.solutions.pose.Pose(...)`が実行されると、`self.pose`には実際のMediaPipeインスタンスではなく、我々が完全に制御できる`mock_pose_instance`が代入されます。
-   **`yield mock_pose_instance`**: `yield`キーワードは、フィクスチャがテスト関数に渡す値を指定します。この場合、テスト関数は`Pose`クラスの*インスタンス*のモックである`mock_pose_instance`を受け取ることになります。これにより、各テストケースは`process`や`close`といったインスタンスメソッドが正しく呼び出されたかを検証できます。

-   **背景**: `PoseEstimator`の初期化パラメータは、推定の精度と速度のトレードオフを決定する重要な要素です。このパラメータが意図せず変更されたり、MediaPipe側に正しく渡されていなかったりすると、アプリケーション全体のパフォーマンスに影響します。このテストは、その設定が正しく行われていることを保証します。
-   **実装の詳解**:
    -   **Arrange**: このテストでは、フィクスチャを使わず、テスト関数内で直接`patch`を使用しています。これは、フィクスチャのセットアップとは少し異なるアサーション（クラスがどう呼ばれたか）を行いたいからです。`with patch("mediapipe.solutions.pose.Pose") as mock_pose_class:`で`Pose`クラスをモック化します。

-   **このテストの重要性**: `PoseEstimator`クラスが、MediaPipeとの契約（データ構造）を正しく理解し、後続モジュールとの契約（Numpy配列形式）を正しく果たしていることを保証する、極めて重要なテストです。

## 第3章: `test_drawing_utils.py` - 視覚的フィードバックの描画ロジックをテストする

このテストファイルは、`src/drawing_utils.py`を対象としています。このモジュールは、姿勢推定のランドマークや動作解析の結果（角度や状態など）を、画像フレーム上に視覚的に描画するための関数群を提供します。ユーザーがリアルタイムで自身の動きを理解するためには、この描画処理が正しく、かつ効率的に行われることが不可欠です。

このテストでは、`PoseEstimator`のテストと同様に、実際に画像ウィンドウを表示したりファイルに書き出したりすることなく、描画ライブラリ（OpenCV, Pillow）の関数が「正しく呼び出されたか」をモッキングによって検証します。これにより、CI/CD環境のようなGUIのない環境でもテストを実行できます。

### 3.1. テストの共通基盤: `dummy_image`フィクスチャ

```python
@pytest.fixture
def dummy_image():
    """テスト用のダミー画像を生成するフィクスチャ"""
    return np.zeros((100, 100, 3), dtype=np.uint8)
```

-   **目的**: 各描画関数の入力として使用する、黒一色のダミー画像（高さ100px, 幅100px, 3チャンネルのカラー）を生成します。
-   **背景**: 描画関数のテストでは、描画ロジックそのものが重要であり、入力画像の具体的な内容は問題ではありません。このフィクスチャは、テストごとに同じサイズの空のキャンバスを用意する手間を省きます。

### 3.2. `test_draw_landmarks` - 骨格ランドマーク描画の検証

-   **目的**: `draw_landmarks`関数が、与えられたランドマーク座標に基づき、OpenCVの`cv2.circle`（点を描画）と`cv2.line`（線を描画）を期待される回数だけ呼び出すことを確認します。
-   **背景**: この関数は、検出された33個のランドマークを点として、また、それらを繋ぐ骨格を線として描画します。正しく描画されるためには、全ての点と、定義された全ての接続線に対して描画処理がループ実行される必要があります。
-   **実装の詳解**:

## 第5章: `test_head_shake_detector.py` - 周期的な頭部動作の検出ロジックをテストする

この種の時系列パターン認識のテストは、単一フレームの静的な姿勢をテストするよりも複雑です。**テストケースは、`for`ループを用いて複数の連続するフレームをシミュレートし、意図的に振動パターンを持つランドマークのシーケンスを生成して`update`メソッドに供給する**というアプローチを取ります。

### 5.2. `test_detect_oscillation_pattern_positive` & `negative` - 振動検出アルゴリズムの単体テスト

-   **目的**: `HeadShakeDetector`の内部で使われているヘルパーメソッド `_detect_oscillation_pattern` のロジックを直接テストします。このメソッドは、角度の時系列リストを受け取り、それが設定された閾値を超える振動パターンを含んでいるかどうかを判定します。
-   **背景**: クラス全体の動作をテストする前に、その中核をなすアルゴリズムを単体でテストすることは、問題の切り分けを容易にするための良いプラクティスです。
-   **実装の詳解**:

    -   **Negative Case**: `[5] * 20`という、値が全く変化しないリストを与えます。これは振動が全くない状態です。このデータをアルゴリズムに与え、`False`が返ってくることを確認します。
-   **このテストの重要性**: 振動を検出するための数学的なロジック（ピークとボトムを見つけ、その数と振幅を評価する）が、理想的な入力に対して正しく機能することを保証します。

### 5.3. `test_update_static` - 静止状態の検証

-   **背景**: 振動を検出するだけでなく、「振動していない」ことを正しく判定するのも同じくらい重要です。これにより、ユーザーが静止しているにもかかわらず、誤って首振りとして検出されることを防ぎます。

### 5.4. `test_head_turn` - 静的な頭の向きの検証

### 5.5. `test_horizontal_shake` - 水平首振り（イヤイヤ）の検出

-   **実装の詳解**:

-   **このテストの重要性**: 静的な状態の組み合わせではテストできない、時間的なパターン認識ロジックが正しく機能することを証明します。システムの動的な解析能力を保証する上で不可欠です。

### 5.6. `test_vertical_nod` - 垂直首振り（ウンウン）の検出

## 第6章: `test_detect_joint_movement_with_hip_stay.py` - 複合的なシナリオベースの動作検出をテストする

### 6.2. `TestPostureMonitor` - 長時間の前傾姿勢監視ロジックのテスト

`PostureMonitor`クラスは、「設定された監視期間（例: 5秒）のうち、危険な前傾姿勢であった時間の割合が、設定された閾値（例: 50%）を超えた場合にアラートを発する」というロジックを実装しています。

-   **`setUp`**: 各テストの前に、`PostureMonitor(monitoring_duration=5.0, alert_threshold=0.5)`で、監視期間5秒、アラート閾値50%のモニターを初期化します。
-   **`_create_dummy_results`ヘルパーメソッド**: このテストクラスの巧妙な点です。引数`is_leaning`に応じて、「明らかに前傾姿勢」または「明らかに直立姿勢」を示すダミーの解析結果辞書を生成します。これにより、各テストケースは「前傾」か「直立」かを指定するだけで、テストシナリオを簡単に構築できます。
-   **`test_update_and_history_management`**:
    -   **目的**: `update`メソッドが、内部に保持する姿勢の履歴（`posture_history`）を、設定された監視期間（5秒）に基づいて正しく管理しているか（古いデータを適切に破棄しているか）を検証します。
    -   **実装の詳解**: まず0秒から4秒まで5つのデータを追加し、履歴が5つになることを確認します。次に6秒のデータを追加すると、監視期間（6.0 - 5.0 = 1.0秒より前）を外れる0秒のデータが削除され、履歴の長さが5のままで、最初の要素が1秒のデータに更新されていることを確認します。
-   **`test_is_forward_leaning_posture`**:
    -   **目的**: `PostureMonitor`の内部ロジックである、単一フレームの解析結果から「前傾姿勢かどうか」を判定し、その「前傾スコア」を計算するメソッドの正しさを検証します。
    -   **実装の詳解**: `_create_dummy_results`で生成した「前傾」データと「直立」データそれぞれについて、判定結果（`True`/`False`）とスコア（`>0.5`/`<0.5`）が期待通りであることを確認します。
-   **`test_alert_triggering`**:

    -   **実装の詳解**: 0秒から5秒まで、6フレーム分のデータを`update`に投入します。最初の4フレームは前傾、後の2フレームは直立とします。最後の6フレーム目（`timestamp=5.0`）の`update`呼び出し時に、過去5秒間の履歴（1秒から5秒まで）が評価されます。この履歴には前傾が3フレーム、直立が2フレーム含まれるため、前傾率が3/5=60%となり、閾値の50%を超えます。したがって、このタイミングでアラートが返されることを`assertTrue(alerts)`で検証します。
-   **`test_alert_cooldown`**:
    -   **目的**: 一度アラートが発火した後、短時間で再びアラウザルな状態が続いても、迷惑にならないように、設定されたクールダウン期間中はアラートを抑制する機能が正しく働くことを確認します。
    -   **実装の詳解**: 最初にループで意図的にアラートを発火させます。その後、`monitor.last_alert_time`を現在時刻に設定し、クールダウン期間内に再度アラート条件を満たすデータを投入しても、アラートリストが空のままであることを確認します。さらに、クールダウン期間が過ぎた後であれば、再びアラートが正常に発火することも確認し、クールダウン機能が正しくリセットされることも検証しています。

### 6.3. `TestHipBasedStayDetector` - 腰の位置に基づく滞在・移動検出のテスト

`HipBasedStayDetector`クラスは、「腰の中心位置が、設定された閾値（ピクセル単位または正規化された距離）を超えて移動したかどうか」を判定します。急な動きを誤検出しないように「猶予期間（grace period）」の概念を取り入れている点が特徴です。

-   **`setUp`**: テスト用の検出器を初期化します。`spike_threshold=1.0`と非常に小さな値に設定することで、テストでわずかな動きでも検知できるようにしています。また、`use_normalization=True`と`normalization_base="torso"`は、移動距離を絶対的なピクセル数ではなく、胴体の長さに対する相対的な割合で評価する設定であり、カメラからの距離が変わっても頑健な検出を可能にするための重要なオプションです。
-   **`_create_dummy_landmarks`**: このテスト用のヘルパーメソッドは、指定された正規化y座標に腰が来るように、また胴体の長さが一定になるようにダミーのランドマークを生成します。これにより、「腰がy方向に0.5の位置にいる」「腰がy方向に0.8の位置に移動した」といったシナリオを簡単に作ることができます。
-   **`test_state_transition_stay_to_move`**:
    -   **目的**: 状態が`STAYING`（滞在中）から`POTENTIAL_MOVE`（移動の可能性あり）へ正しく遷移するかをテストします。
    -   **実装の詳解**: 最初に`y=0.5`の位置で`update`を呼び、初期位置を記録させます。次に`y=0.8`という大きく動いた位置のランドマークで`update`を呼びます。この移動量は`spike_threshold`を超えるため、状態が`POTENTIAL_MOVE`に遷移することをアサートで確認します。
-   **`test_state_transition_move_to_stay`**:
    -   **目的**: `POTENTIAL_MOVE`状態になった後、それが一時的なスパイクノイズのようなもので、すぐに静止した場合（誤報だった場合）、猶予期間が過ぎると状態が`STAYING`に復帰することをテストします。
    -   **実装の詳解**: まず`POTENTIAL_MOVE`状態に移行させます。その後、動いた先の位置（`y=0.8`）で静止したランドマークを、猶予期間（1.0秒）が過ぎるまで与え続けます。猶予期間を過ぎた`timestamp=2.1`の時点で`update`を呼び出すと、結局大きな移動は確定しなかったと判断され、状態が`STAYING`に戻ることを確認します。この時、滞在の開始地点は新しい位置に更新されます。
-   **`test_state_transition_move_confirmed`**:
    -   **目的**: `POTENTIAL_MOVE`状態になった後、猶予期間中も動きが継続した場合に、移動が確定し、アラートが発せられ、滞在情報がリセットされることをテストします。
    -   **実装の詳解**: `POTENTIAL_MOVE`状態に移行させた後、猶予期間内にさらに別の位置（`y=0.5`）に動くランドマークを与えます。猶予期間を過ぎた時点で`update`を呼び出すと、移動が確定したとみなされ、`"[!] Movement Confirmed"`というアラートが返されることを確認します。また、状態が`STAYING`に戻り、滞在開始時間（`stay_start_time`）が新しい現在時刻にリセットされていることも確認します。
-   **`test_long_stay_alert`**:
    -   **目的**: 腰の位置が全く動かないまま、設定された滞在閾値（`stay_threshold_sec=5.0`）を超えた場合に、長期滞在アラートが正しく発火することをテストします。
    -   **実装の詳解**: ループを使って0秒から5秒まで、全く同じランドマークで`update`を呼び出し続けます。`timestamp=5.0`の呼び出しで滞在時間が閾値に達するため、`"[!] Long Stay Detected"`というアラートが返されることを確認します。また、一度通知したらずっと通知し続けないように、`notified`フラグが`True`になることも確認します。

### 6.4. `TestKneeAngleMonitor` - 膝角度の継続的な監視ロジックのテスト

`KneeAngleMonitor`クラスは、「膝の角度が、設定された危険な閾値（例: 90度）を下回る状態が、一定期間継続している場合にアラートを発する」という、より専門的な監視ロジックを実装しています。単発の危険な角度ではなく、**継続性**を評価するために、秒単位での角度の**中央値**と、さらにその数秒間にわたる**移動平均**という2段階の評価を行います。

-   **`setUp`**: 危険角度を90度、移動平均のウィンドウを3秒に設定したモニターを初期化します。
-   **`_create_dummy_results`**: 指定された角度を持つ、ダミーの膝関節解析結果を生成するヘルパーメソッドです。
-   **`test_angle_accumulation_and_finalization`**:
    -   **目的**: フレームごとに入力される角度データが、内部で秒単位（例: 0秒台、1秒台）に正しくグループ化され、次の秒に移ったタイミングで前の秒の角度リストの中央値が計算・確定される、という集計ロジックを検証します。
    -   **実装の詳解**: `timestamp`が0.1, 0.2, 0.3のデータを投入します。この時点ではまだ0秒台です。次に`timestamp=1.1`のデータを投入すると、ここで初めて「0秒台の集計期間が終わった」と判断され、0秒台のデータ（80.0, 80.0, 120.0）の中央値である80.0が計算され、`medians_history`に格納されることを確認します。
-   **`test_confidence_threshold`**:
    -   **目的**: ランドマークの検出信頼度が低いデータは、ノイズである可能性が高いため、角度の集計から除外されることを確認します。
    -   **実装の詳解**: 信頼度が`0.4`（閾値`0.5`未満）のダミーデータを投入します。集計が確定するタイミングになっても、このデータは無視されているため`medians_history`が空のままであることを確認します。
-   **`test_alert_triggering_by_median`**:
    -   **目的**: ある秒の角度の中央値が、単体で危険閾値を下回った場合に、即座にアラートが発火することを確認します。
    -   **実装の詳解**: 0秒台に危険な角度（80.0）を投入します。1秒台のフレームが来た時点で0秒台の集計が確定し、中央値（80.0）が閾値（90.0）を下回るため、アラートが生成されることを確認します。
-   **`test_alert_triggering_by_moving_average`**:
    -   **目的**: 単発の中央値は安全域でも、危険域に近い値が数秒間続いた結果、中央値の移動平均が閾値を下回った場合に、アラートが発火することを確認します。
    -   **実装の詳解**: 0秒台、1秒台、2秒台にわたって、危険な角度（80.0）を記録させます。これにより、`medians_history`には3秒分の危険な中央値が蓄積されます。3秒台のフレームが来た時点で、過去3秒間の移動平均が計算され、それが閾値を下回るため、移動平均（MA）によるアラートが生成されることを確認します。
-   **`test_no_alert`**:
    -   **目的**: 膝の角度が常に安全な範囲（120.0度）にある場合は、どのようなアラートも発火しないことを確認します。
    -   **実装の詳解**: 安全な角度データのみを投入し続け、`update`の返り値が常に空（アラートなし）であることを確認します。

-   `test_src_definitions.py`は**プロジェクトの共通言語**を固め、
-   `test_drawing_utils.py`は**ユーザーへの視覚的フィードバック**を保証し、
-   `test_movement_analyzer.py`は**基本的な物理法則（角度計算）**の正しさを検証し、
-   `test_head_shake_detector.py`は**時間軸上の単純なパターン認識**をテストし、
-   `test_detect_joint_movement_with_hip_stay.py`は**複数の条件を組み合わせた、より高度なビジネスロジックに近いシナリオ**をテストします。

このように、ユニット（単体）レベルから、複数の条件を組み合わせた小さなインテグレーション（統合）レベルまで、テストが階層的に構成されています。巧妙に作成されたダミーデータと、モッキングを駆使した依存関係の分離により、実際のカメラや複雑な環境なしに、ロジックの隅々までを網羅的かつ自動的に検証できる体制が整えられています。

この堅牢なテストスイートこそが、リアルタイム動作解析という不確実性の高いタスクを実行するアプリケーションに、信頼性と安定性をもたらすための礎となっているのです。
