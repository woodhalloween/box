# Coding Rules for Python/Pythonのコーディング規約

# 概要

---

## 🇯🇵 日本語 (Japanese): Python コーディングルールの目的とメリット

### **「Python でコードを書くなら、適当にやるな。最初から"戦略的に"組み立てるべきだ。」**

Python のコーディングルールは、単なるスタイルガイドではない。

それは **「戦場での作戦指揮」** のようなものだ。適切な設計をすれば、チーム全体がスムーズに動ける。逆に、無計画にコードを書けば、いずれ技術的負債に足を取られ、身動きが取れなくなる。

このルールを徹底する理由は明確だ。

- **可読性の向上**：「何が起きているのか、一瞬で理解できるコード」にする。
- **バグの防止**：「バグを生みにくい設計」と「即座に異常を検出できる構造」を組む。
- **パフォーマンスの最適化**：「非効率なコードは敵だ。処理を最適化し、大規模データにも耐えうる設計をする。」
- **拡張性の確保**：「どんな未来にも適応できるように、柔軟な設計を採用する。」

### **Python の設計ルールの要点**

1. **関数・クラスの設計**：明確な命名 (`snake_case`, `PascalCase`)、型ヒント、純粋関数を意識する。
2. **デザインパターンの活用**：パイプライン、ファクトリ、ストラテジーなど、適切な設計パターンを選ぶ。
3. **プロジェクト構造**：各ファイルの役割を明確にし、モジュール化を徹底する。
4. **ロギングとエラーハンドリング**：異常を即座に検知し、適切に処理するための仕組みを整える。
5. **テスト戦略**：ユニットテスト・統合テスト・CI/CDを組み込み、品質を維持する。
6. **環境管理**：`venv`, `poetry`, `conda` を活用し、依存関係を管理する。
7. **データ検証とスキーマ管理**：`pydantic` や `marshmallow` でデータ整合性を担保する。
8. **並列化とスケーラビリティ**：`multiprocessing`, `Dask`, `Spark` などを活用し、負荷に耐える設計を採用する。

「適当なコードを書くのは、適当な装備で戦場に出るようなものだ。」

戦う前に、戦略を立てろ。**ルールを守れば、Python という武器を最大限に活かせる。**

# 詳細

---

### 🇯🇵 日本語 (Japanese)

**1. ベストプラクティス (Best Practices)**

- **一般的なガイドライン (General Guidelines)**
    - **変数・関数・クラスの命名規則 (Naming Conventions in English)**
        - 変数、関数、クラス名には **アメリカ英語** をデフォルトで使用する。
        - **分かりやすい名前を使用する**: 関数名・クラス名は直感的で、**PEP 8** の規約に従う（関数名は `snake_case`、クラス名は `PascalCase` を使用）。
    - **コメントは日本語で記述 
        - 詳細はこちらを参照してください。
    
    - **可読性と明瞭性 (Clarity and Readability)**
        - [**PEP 8**](https://peps.python.org/pep-0008/) のコードスタイルガイドライン（インデント、行の長さ、空白の使い方など）を遵守する。
        - 関数名やクラス名は **自己説明的 (self-explanatory)** にし、コードの可読性を向上させる。
- **ファイルの最適化 (File Optimization)**
    - **関心の分離 (Separate Concerns)**: 各ファイルは **特定の機能にのみ責任を持つ** ようにし、過度に結合しないようにする。
- **実装の最適化 (Implementation Optimization)**
    - **パフォーマンスの最適化 (Optimize for Performance): `numpy` や `pandas` のベクトル化演算 (vectorized operations)** を使用し、大規模データセットの処理で非効率なループを回避する。
- **国際化（オプション） (Internationalization - Optional)**
    - 多言語対応が必要な場合は、`gettext` などの **i18nライブラリ** を活用する。
    - ただし、**内部のコードロジック（変数、関数、クラス名）は英語で統一** し、グローバルなコラボレーションを容易にする。

**2. 関数・クラスの定義 (Function and Class Definitions)**

- **型ヒント（Type Hints）とドックストリング（Docstrings）**
    - 入出力の型を明示し、**PEP 257** に準拠した簡潔なドックストリングを記述する。
- **副作用を避ける (Avoid Side Effects)**
    - **関数は可能な限り純粋関数 (pure function) にする**（グローバル変数を変更しない）。
    - データ分析パイプラインの再現性を確保するため、**関数の入力が同じなら出力も同じになるように設計する**。
- **`@staticmethod` & `@classmethod` を適切に使う**
    - インスタンスの状態を変更しないメソッドには **`@staticmethod` または `@classmethod`** を使用し、明瞭性を向上させる。
- **構造化データには `@dataclass` を使用する**
    - 構造化データ（例：データセットのメタデータや特徴量定義）を扱う場合は、可読性と保守性を向上させるために `@dataclass` を利用する。

**3. データ分析向けのデザインパターン (Design Patterns for Data Analytics)**

- **パイプラインパターン (Pipeline Pattern):**
    - データ処理ワークフローを**一連の変換ステップ**として構成する（例：データ取得 → 前処理 → 特徴量エンジニアリング → モデリング → 評価）。
    - **実装例:**

```python
class DataPipeline:
    def __init__(self):
        self.steps = []

    def add_step(self, step):
        self.steps.append(step)

    def execute(self, data):
        for step in self.steps:
            data = step.process(data)
        return data
```

- **ファクトリパターン (Factory Pattern)**
    - 実行時の要件に応じて、**モデルや処理ユニットを動的にインスタンス化** するためのパターン。
- **ストラテジーパターン (Strategy Pattern)**
    - **異なる処理戦略**（例：複数の特徴選択手法）を**柔軟に切り替え可能にする**ための設計手法。

**4. ファイルの割り当てとプロジェクト構造 (File Allocation and Project Structure)**

- **モジュール化されたスケーラブルなプロジェクト構造**を維持するため、以下のディレクトリ構成を推奨:

```python
project_root/
│── data/                     # 生データ、処理済みデータ、結果データ
│── src/                      # ソースコード
│   ├── __init__.py           # モジュール識別用
│   ├── data_loader.py        # データ取得処理
│   ├── preprocess.py         # データ前処理・特徴量エンジニアリング
│   ├── models.py             # 機械学習モデル
│   ├── evaluation.py         # モデル評価
│   ├── visualization.py      # データ可視化
│   ├── utils/                # ユーティリティ（ログ管理、設定管理など）
│── notebooks/                 # Jupyter Notebook
│── tests/                     # ユニットテスト・統合テスト
│── requirements.txt           # 依存関係
│── config.yaml                # 設定ファイル
│── README.md                  # ドキュメント
```

**5. ロギングとエラーハンドリング (Logging and Error Handling)**

- **`logging` モジュールを使用**（`logging.getLogger(__name__)`）して、統一されたロギングを確保する。
- 例外処理を**標準化**し、重要なパイプラインステップのデバッグを容易にする（例：カスタム例外クラスを作成）。

**6. テスト戦略 (Testing Strategy)**

- **ユニットテスト、統合テスト、パフォーマンステスト**を実施する。
- **CI/CDパイプラインにテストを統合**（例：GitHub Actions, Jenkins）し、品質を継続的にチェックする。

**7. 環境と依存関係の管理 (Environment and Dependency Management)**

- **`venv`、`conda`、`poetry` などを活用**し、環境を分離して再現性を確保する。
- `requirements.txt` や `poetry.lock` を使用し、依存関係のバージョンを固定する。

**8. データ検証とスキーマの強制 (Data Validation and Schema Enforcement)**

- データ分析タスクでは、**受信データの検証** を行い、**正確性と一貫性を確保** する（例：`pydantic` や `marshmallow` を使用）。
- **期待されるスキーマをドックストリングまたは別の設定ファイルに記述する** ことで、データ構造を明確にする。

**9. Parallelization and Scalability 並列化とスケーラビリティ (Parallelization and Scalability)**

- **大規模データ処理では並列処理や分散処理を活用**（例：`multiprocessing`、Dask、Spark）。
- モジュールやパイプラインをスケールアップしやすい設計にする。
