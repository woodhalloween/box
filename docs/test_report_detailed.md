# テスト実装 詳細報告書

## 1. 概要

本報告書は、`src/` および `scripts/` ディレクトリ配下のPythonコードベースに対して実施された、一連の単体テストおよび統合テストに関する詳細な経緯、結果、そしてその過程で得られた知見をまとめたものである。

当初の目的は、コードの品質を保証し、将来的な変更による意図しない品質低下（デグレード）を防止するためのテストスイートを構築することにあった。しかし、プロジェクトは単なるテストコードの追加に留まらなかった。テストを実装するプロセスそのものが、極めて強力なコードレビューおよびデバッグツールとして機能し、これまで潜在していた数多くの設計上の問題やバグを白日の下に晒した。

特に、状態を持つ複雑な分析モジュールや、外部ライブラリと連携するモジュールにおいては、テストケースを作成し、それをパスさせようと試みる中で、ロジックの根本的な欠陥が次々と明らかになった。結果として、テスト実装はコードの品質を「テスト駆動でリファクタリング」する活動へと発展した。本報告書では、その困難を極めた道のりと、コードベースがいかにしてより堅牢で保守性の高いものへと改善されていったかを詳細に記録する。

## 2. テスト基盤の構築と初期課題の克服

テスト実装に着手した最初の段階で、プロジェクトの構造に起因する根本的な課題に直面した。

### 2.1. 課題: `ModuleNotFoundError`
テスト対象のソースコードが `src/` ディレクトリに、テストコードが `tests/` ディレクトリに配置されている構成において、テストコード内から `from src.definitions import ...` のようなインポート文を実行すると、Pythonインタープリタが `src` モジュールを見つけられず `ModuleNotFoundError` が発生した。

これは、テストランナー(`pytest`)がプロジェクトのルートディレクトリから実行された際に、`src` ディレクトリがPythonの検索パスに含まれていないために起こる典型的な問題である。

### 2.2. 解決策: プロジェクトのパッケージ化
この問題を恒久的に解決するため、場当たり的なパス修正（`sys.path.append`など）ではなく、プロジェクトの構成をより現代的で標準的なものへと変更するアプローチを採用した。

1.  **`pyproject.toml` の設定変更**: Pythonのパッケージ管理ツールであるPoetryの設定ファイル `pyproject.toml` を編集した。`[tool.poetry]` セクションに `packages = [{include = "src"}]` という設定を追加し、`package-mode = false` を削除した。これは、Poetryに対して「`src` ディレクトリをこのプロジェクトのメインとなるインストール可能なパッケージとして扱う」よう指示するものである。
2.  **`poetry install` の実行**: 設定変更後、`poetry install` コマンドを実行した。これにより、`src` パッケージが編集可能モード（editable mode）でプロジェクトの仮想環境にインストールされる。
3.  **結果**: この手順により、`src` ディレクトリはプロジェクト内のどこからでも正しくインポート可能なパッケージとして認識されるようになり、`ModuleNotFoundError` は完全に解消された。これは、テスト実行の安定性を確保する上で不可欠な最初のステップとなった。

## 3. `src`ディレクトリ: コアロジックの単体テスト詳細

テスト基盤の確立後、プロジェクトの心臓部である `src` ディレクトリ内の各モジュールに対する単体テストを、依存関係の少ないものから順に実装した。

### 3.1. ユーティリティと定義ファイル
`definitions.py` や `pose/utils.py` のような、状態を持たない純粋な関数や定数を定義するモジュールは、テストの初期段階で実装した。これらのテストは、期待される定数値が正しいか、あるいは特定の入力に対して関数が正しい計算結果を返すかを確認するもので、問題なく成功した。これらは、構築したテスト環境が正しく機能していることを確認するための試金石となった。

### 3.2. 外部ライブラリ依存モジュールのテスト (モックの活用)
`drawing_utils.py` (OpenCVを利用) や `pose_estimator.py` (MediaPipeを利用) は、テストにおいて特別な配慮が必要だった。

-   **課題**: これらのモジュールを直接テストしようとすると、テスト実行のために重量級の外部ライブラリ（OpenCV, MediaPipe）が必要となり、テストは低速になる。また、画像ファイルの生成やモデルのダウンロードといった副作用を伴い、テスト環境の構築も複雑になる。
-   **解決策**: `pytest-mock` ライブラリを全面的に活用した。モックとは、本物のオブジェクトの「偽物（スタブ）」を作成し、本物の代わりにふるまわせる技術である。例えば、`drawing_utils.py` のテストでは、実際の `cv2.line` 関数をモックオブジェクトに置き換えた。そして、テスト対象の関数を実行した後、「モック化された `cv2.line` が、期待される座標や色といった引数で正しく1回呼び出されたか」をアサート（検証）した。これにより、実際の画像を描画することなく、我々のロジックが意図通りにOpenCVを利用しようとしていることを高速かつ独立して検証できた。

### 3.3. 状態を持つ複雑な分析クラスのテスト

#### 3.3.1. `movement_analyzer.py` - 状態とデータの問題
このクラスは、時系列の姿勢データを分析し、関節の動き（屈曲、伸展など）を判定する。状態（`previous_angles`）を持つため、テストは単純ではなかった。

-   **課題1（状態の管理）**: あるテストケースで `FLEXION`（屈曲）をテストすると、クラスインスタンスの内部状態が「屈曲した状態」に変化する。その同じインスタンスを次のテストケースで `EXTENSION`（伸展）のテストに使用すると、テストは失敗する。なぜなら、テストが期待する「静止状態」から始まっていないからだ。
-   **解決策1（テストの分離）**: `pytest.fixture` を利用して、テスト関数ごとに `MovementAnalyzer` の新しいインスタンスを生成する仕組みを導入した。これにより、各テストは常にクリーンな状態で開始され、互いに影響を及ぼさないようになった。
-   **課題2（テストデータの不安定性）**: 当初、ランダムな値で生成したダミーのランドマークデータを使用していたため、偶然の座標配置によってテストが時折失敗する「 flaky test（不安定なテスト）」が発生した。
-   **解決策2（安定したテストデータ）**: `stable_landmarks` という名前の固定フィクスチャを作成した。これは、人間が自然に直立した状態を模した、現実的で予測可能な座標セットである。各テストシナリオでは、この安定したデータをベースに、特定の関節点（例：右手首）の座標のみを意図的に変更することで、特定の動きを正確にシミュレートし、テスト結果の信頼性を確保した。

#### 3.3.2. `detect_joint_movement_with_hip_stay.py` - バグ発見の宝庫
この巨大なモジュールは、複数の分析クラス（`PostureMonitor`, `HipBasedStayDetector`, `KneeAngleMonitor`）を内包しており、テスト実装の過程でソースコードの複数のバグが発見・修正された。

-   **`PostureMonitor` のバグ**: 前傾姿勢が続いた場合にアラートを出すこのクラスには、クールダウン処理にロジックエラーがあった。`self.last_alert_time` が `0` で初期化されるのに対し、クールダウンのチェックが `current_time - self.last_alert_time < cooldown_duration` となっていた。テストシナリオでは `current_time` も `0` から始まるため、この条件が常に真となり、**初回のアラートが絶対に発火しない**という致命的なバグが存在した。これは、`if self.last_alert_time > 0 and ...` という条件を追加することで修正された。
-   **`KneeAngleMonitor` のバグ**: このクラスは、秒単位で膝の角度を集計し、その中央値や移動平均を計算する複雑なロジックを持っていた。テストは最も難航し、その過程で**データ集計タイミングのバグ**が発見された。具体的には、「次の秒の最初のフレーム」のデータが、「前の秒のデータを集計する」処理の**前に**リストに追加されてしまっていた。例えば、0.9秒までのデータの中央値を計算すべきところに、1.0秒のデータが混入し、計算結果がずれていた。これは、`update` メソッド内の処理順序を「1. 前の秒の集計を確定させる → 2. 現在のフレームのデータを追加する」という正しい順序に入れ替えることで修正された。

#### 3.3.3. `head_shake_detector.py` - テスト駆動リファクタリングの実践
このモジュールのテストは、今回の取り組みにおける最大の挑戦であり、テストがコード品質をいかに向上させるかを示す最良の事例となった。

-   **根本原因（不安定な計算ロジック）**: 当初の角度計算ロジックは、`math.atan2` の差分を利用する複雑なもので、非常に不安定だった。例えば、**視覚的には完全に正面を向いているランドマークデータを与えても、計算結果が-90度となり、即座に `HEAD_LEFT_TURN` と誤判定された**。このため、「静止状態をテストする」という最も基本的なテストケースすら作成できなかった。
-   **リファクタリングの過程**: この問題を解決するため、テストデータや閾値を微調整する小手先の修正を何度も試みたが、全て失敗に終わった。最終的に、計算ロジックそのものが根本的に欠陥を抱えていると結論付け、全面的なリファクタリングに踏み切った。
-   **解決策（シンプルで堅牢な新ロジック）**: 複雑な三角関数を捨て、「**両耳の中点に対する鼻の水平方向のズレを、両耳間の距離で正規化したもの**」を角度として採用した。この新しい指標は、物理的な頭の向きと直感的に一致し、予測可能で安定している。テストが容易な設計を追求した結果、実装そのものが改善されるという、テスト駆動開発の理想的なサイクルが実現した。
-   **最後の課題（`deque` のタイミング問題）**: ロジック修正後も、振動検出テストが失敗した。原因は、角度の履歴を保持する `deque`（固定長キュー）の更新タイミングにあった。振動チェックが行われる**前に**新しいデータが `deque` に追加され、最も古いデータが押し出されていたため、常に不完全な履歴データで判定が行われていた。これは、テストコード側で `update` の呼び出しタイミングを調整し、状態遷移と振動検出のタイミングを正しく分離することで最終的に解決した。

## 4. `scripts` ディレクトリ: 統合テストと堅牢性の向上

`src` ディレクトリのコアロジックとは異なり、`scripts` ディレクトリ内のスクリプトは、コマンドラインから実行され、ファイルシステムと直接やり取りする。そのため、テストは `subprocess` モジュールを用いた統合テストとして実装された。

### 4.1. 共通していた課題と改善
テスト対象となった `clip_video_by_frame.py` と `clip_segments_by_idea.py` には、共通の設計上の問題があった。

-   **課題1（引数解析の脆弱性）**: 両スクリプトとも、`sys.argv` を直接インデックスで参照して引数を解釈する、旧来の脆弱な実装だった。引数の順序を間違えると容易に破綻し、テストコードからの自動実行も困難だった。
-   **改善1（`argparse`の導入）**: これらのスクリプトをリファクタリングし、Pythonの標準ライブラリである `argparse` を用いて、`--input-path` のような明確なキーワード引数を受け取るように全面的に書き換えた。これにより、スクリプトの使い勝手と可読性、そしてテストの容易性が劇的に向上した。
-   **課題2（入力値検証の欠如）**: テストを実装する中で、両スクリプトともに**入力値の検証が全く行われていない**というバグが明らかになった。存在しない動画ファイルを指定してもエラーにならず、不正なフレーム範囲を指定しても何の警告もなく処理を進めようとしていた。
-   **改善2（エラーハンドリングの追加）**: スクリプトの冒頭に、`os.path.exists()` を用いたファイル存在チェックや、引数の妥当性（例：終了フレーム > 開始フレーム）を検証するロジックを追加した。不正な入力が与えられた場合は、明確なエラーメッセージを出力し、非ゼロの終了コードで即座に終了するように修正した。これにより、スクリプトの堅牢性が大幅に向上した。

## 5. 総括と今後の展望

今回の一連のテスト実装は、単にコードの振る舞いを検証する受け身の活動ではなく、コードベース全体の品質を積極的に監査し、向上させるための原動力となった。テストを書くという行為を通じて、設計の曖昧さ、潜在的なバグ、そして保守性を損なう実装が浮き彫りになり、それらを修正・リファクタリングする具体的な指針が得られた。結果として、プロジェクトのコア機能は、以前とは比較にならないほど堅牢で信頼性の高いものとなった。

今後の課題としては、`scripts/evaluation` ディレクトリ配下の評価用スクリプト群のテストが未実装であることが挙げられる。これらのスクリプトは、機械学習モデルの実行を伴う可能性が高く、長時間の処理が必要となるため、これまでのテスト手法をそのまま適用するのは非現実的である。

この課題に対しては、モデルの推論部分そのものをモック化し、ダミーの推論結果を返すようにすることで、モデル実行のコストをかけずに、その前後のデータ処理や評価指標の計算ロジックを単体テストするハイブリッドなアプローチが有効と考えられる。

今回構築したテストスイートは、今後の開発における強力なセーフティネットとして機能するだろう。新しい機能を追加したり、パフォーマンス改善のためのリファクタリングを行ったりする際に、既存の機能が壊れていないことを自動的に保証してくれるこの資産は、プロジェクトの持続的な成長に不可欠なものである。
